## Prompt

# Artifact under review: revision 2 of the development loop

A previous audit of revision 1 returned RECOMMENDATION: reject with five
findings. Revision 2 below is the response. Your job is to decide whether each
finding is actually closed, and to attack whatever revision 2 introduces.

## The five findings from the previous audit, restated

F1 (critical) Transformation gap. The loop validated the integrity of knowledge
   but never the integrity of translation. Nothing checked that DESIGN reflects
   RESEARCH or that CODE reflects DESIGN; such an error would surface only at
   the next RESEARCH phase, after the code was already written.
F2 (major) No independent agency. The team is one human plus AI agents, so the
   "independent party" performing AUDIT may share context with the researcher.
F3 (moderate) Economic justification paradox. Boehm's cost-escalation argument
   is used to justify front-loading, but the team's own evidence (Menzies, 171
   projects, no delayed issue effect) undercuts it.
F4 (minor) "Machine checks" at VERIFY was an empty placeholder.
F5 (minor) Evidence supports the existence of phases, not this ordering.

## Revision 2

The loop is now stated as two nested loops, not one.

OUTER LOOP (per increment of scope; slow; the human is in it)

    RESEARCH -> AUDIT -> VERIFY(human gate) -> DESIGN -> CODE
       ^                                                   |
       +-------------------- FEEDBACK ---------------------+

INNER LOOP (per change; fast; fully mechanical; no human)

    every DESIGN item is written as a NAMED FALSIFIABLE OBLIGATION with a
    machine oracle attached before any code is written for it. Each obligation
    has the shape:

        id, one-sentence claim, the executable check that decides it,
        and the observable value the check must produce.

    CODE is not "done" until its obligations' oracles pass. An obligation
    without an oracle cannot enter DESIGN.

Concrete oracles that already exist in this project and would be attached:
  - a determinism digest: 2000 ticks x 400 entities reduced to a single FNV-1a
    chained hash, currently 0xfc60aadd. Any behavioural change to the
    simulation changes this number.
  - GPU parity: the WGSL compute shader is executed on a software Vulkan device
    in CI and compared bit-for-bit against the TypeScript reference executor,
    per tick, producing digest 0x1f3865c0.
  - a fixed-point oracle: Q16.16 multiply/divide/sqrt checked against exact
    BigInt arithmetic.
  - a trigonometry oracle: CORDIC output checked against an error budget of 24
    Q16.16 units.
  - a render check: the shader draws to an offscreen texture and the pixels are
    inspected; a flag turns "no GPU adapter found" from a skip into a failure.
  - a governance check: a machine test that fails the build if the economy
    config contains dark patterns, loss-framing, artificial scarcity timers,
    streak-punishment, or a non-graceful session end.

Responses to the findings:

R1 (to F1) The inner loop is the answer. DESIGN cannot contain an item without
   an oracle, so DESIGN->CODE conformance is decided mechanically on every
   change rather than at the next RESEARCH phase. The Q16.16-vs-Q8.24 test the
   previous auditor proposed would be caught by the determinism digest changing.

R2 (to F2) The AUDIT step runs on a different model from a different vendor,
   reached over that vendor's API, and is given the artifact without the
   reasoning that produced it. Every audit exchange is written to a transcript
   file so a finding can be traced to a recorded request and response. The
   human is not the auditor; the human is the approver at VERIFY.

R3 (to F3) The ordering is no longer justified by cost-escalation. It is
   justified by irreversibility: RESEARCH and AUDIT are cheap to redo and
   produce no artifacts that must be maintained; CODE is expensive to redo and
   produces artifacts that must be maintained forever. Menzies' null result is
   accepted as correct and the Boehm justification is withdrawn.

R4 (to F4) The machine checks at VERIFY are named: the six oracles above, run
   as a suite, plus two secret-scanning checks. VERIFY reports their current
   values to the human approver so the approver sees measured state, not
   claims.

R5 (to F5) Accepted. The evidence is now cited only for the existence and value
   of each phase. The ordering is justified by the irreversibility argument in
   R3, which is the team's own reasoning and is labelled as such.

## What to audit

(a) Does R1 actually close F1? Name a concrete design-to-code translation error
    in this project that would pass every one of the six listed oracles.
(b) Does R2 actually close F2, or is cross-vendor model diversity insufficient
    for independence? What would remain correlated between the two models?
(c) Is the irreversibility argument in R3 sound, or does it have the same
    problem the cost-escalation argument had?
(d) Revision 2 requires that "an obligation without an oracle cannot enter
    DESIGN." What legitimate and necessary design work does that rule forbid,
    and what will the team do instead when it hits that wall?
(e) What is the single most likely way this loop is abandoned in practice after
    three increments? Be specific about which step gets skipped first and why.
