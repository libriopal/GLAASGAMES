# Road to an APK you can test and approve

Ten recommended runs of [`EINCOL.md`](../EINCOL.md), ordered so that the first
wave puts a working build in your hands and nothing after it happens without
your approval.

Generated by running the protocol rather than from memory: the state below was
measured, and one measurement changed the entire ordering.

---

## What the survey actually found

**The APK builds.** `app-release.apk`, `app-debug.apk` and `app-release.aab`
all exist. The Android side is in good shape — no `<uses-permission>` at all
(so Data Safety is "no data collected" and the *platform* enforces it, not a
promise), `targetSdk 36` for the Aug 2026 Play requirement, `minSdk 24`,
release builds left **unsigned** rather than silently falling back to the debug
key, and `BuildConfig.DEBUG` gating WebView remote debugging.

**And the game is not in it.**

```
lattice/ imports in web/ :  0
```

`web/main.ts` imports the engine — `loop`, `rotor4`, `game`, `hash`. It imports
**nothing** from `lattice/`. Every piece of Slice 0 — the 6×6 board, the dice,
commit–reveal, the rules hash, the principal-return bond, the hidden lattice,
frame sync — is verified library code **with no user-facing surface**. The APK
currently ships the 4D engine demo.

Second finding: `verify-render` reports `SKIPPED — no WebGPU`. The renderer
that draws the world has **never been executed in this environment**. Eleven
green checks and the drawing path is not one of them.

That reorders everything. There is no point polishing a build you cannot play.

## Wave A — before you can meaningfully test anything

### 1. Wire Slice 0 into a playable surface
**Cue:** *"What is the smallest user-facing surface that exercises every Slice 0
seam end to end — board, dice, commit, play, reveal, verify — and what does it
prove that the library tests do not?"*

**Evaluator (rung 2):** a scripted playthrough driving the real UI, whose final
score, digest and rules hash must equal `verifyRound`'s recomputation. If the UI
and the verifier disagree, the UI is lying to the player.

**Why this one is first:** everything else on this list is unmeasurable until
it exists. `lattice/` is 1,341 lines of verified code that no user can reach.

**You approve when:** you can play a round on your phone, see the reveal, and
watch the commitment check pass in front of you.

---

### 2. Prove the renderer draws, on real silicon
**Cue:** *"What exactly is unproven about the drawing path, and what is the
cheapest evidence that is not 'it looked right on one screen'?"*

**Evaluator (rung 1):** `verify-render` already renders to a texture it owns and
reads pixels back — it just has no GPU here. Run it under Deno with a Vulkan
device (lavapipe), as `verify-parity` already does. Then the negative control
that matters: **blank the shader and confirm the check goes red.** A pixel
reader that passes on an empty frame proves nothing.

**Why:** `SKIPPED` is not `PASS`, and it has been sitting in the suite output
looking like a pass-adjacent word.

**You approve when:** the suite reports twelve green and zero skipped.

---

### 3. Make the release build have an identity
**Cue:** *"What in the shipped artifact is asserted rather than pinned?"* —
the §3 classifier applied to the APK instead of the source.

**Evaluator (rung 2):** unzip the built APK; verify the signature block, confirm
`android:debuggable` is absent, confirm the staged assets hash to the same
values as `web/dist`, and confirm the rules hash inside the bundle matches
`computeRules()` on the source it was built from.

**Why:** the build correctly refuses to sign with a debug key. That means today
there is no signed artifact at all, and *unsigned* and *unnoticed* look the same
from the outside. Also: nothing currently binds the APK's contents to the source
commit — the exact hole `ruleset.ts` closed for rounds, one level up.

**You approve when:** you install a signed build from a keystore you control.

## Wave B — production grade for an actual submission

### 4. The cold-start path, which is the only one every user takes
**Cue:** *"What happens on the first three seconds of a first-ever launch, on the
slowest device we claim to support?"*

**Evaluator (rung 2):** instrumented launch on an emulator at `minSdk 24`, cold
cache, measuring time-to-first-frame; plus a deliberate WebView failure to see
what the player sees when it does not come up.

**Why:** every other quality issue is conditional on the app opening. This is
also where a WebView app most often fails review — a white screen that a
reviewer reads as "broken".

**You approve when:** you have seen the launch on a slow device and the failure
screen is a message, not a blank.

---

### 5. Device reality, not device assumptions
**Cue:** *"Which claims in this build are true of the developer's device and
assumed of everyone else's?"*

**Evaluator (rung 2 + 3):** run the WebGL2 fallback path against a matrix of
System WebView versions; `verify-controls` already checks layout headlessly
across real viewports, so extend that matrix rather than inventing one.

**Why:** `minSdk 24` claims WebGL2 in the System WebView across the entire
install base. That is a strong claim about a component the user updates
independently of the OS, and it is currently untested below the dev device.

---

### 6. Play policy, aimed at the language rather than the code
**Cue:** *"Which sentence in this submission would a reviewer read as
gambling?"*

**Evaluator (rung 3 — this one genuinely needs an outside reader):** give an
independent model the store listing, the in-app copy and the bond mechanic
**without** the architectural reasoning, and ask what category it falls in.
Your own reasoning is exactly what a reviewer will not have.

**Why:** the mechanic is sound — principal-return, RTP undefined without a
wager, `S1` proves payout equals principal on won/lost/abandoned. But policy
review reads *words*, and "stake", "bond" and "prize" carry meaning you did not
put there. This is a copy audit, not a code audit.

**You approve when:** the outside reader, given only what a reviewer sees,
does not call it gambling.

---

### 7. Observability with no INTERNET permission
**Cue:** *"How do we learn about a crash on a stranger's device when the app
cannot transmit and we consider that a feature?"*

**Evaluator (rung 4, then 2):** write the adversarial case first — a specific
crash on a specific device — and check whether the proposed mechanism would
actually have surfaced it.

**Why:** this is the most interesting constraint in the project and the one
most likely to be solved badly. Adding a crash SDK means adding INTERNET, which
destroys the "no data collected" claim that the platform currently *enforces*.
The design space is on-device only: a local crash log the player can choose to
share, a deterministic replay seed on the error screen. The engine already
records replays — **a bug report could be a seed and an input list**, which is
the whole point of a deterministic engine and is better than a stack trace.

**Do not** let this one drift into "just add Firebase". That is the mode answer.

## Wave C — polish, only after you approve Wave A and B

### 8. Frame pacing, battery, thermal
**Cue:** *"Where does this app spend a phone's battery, and is the fixed
timestep honoured under thermal throttling?"*
**Evaluator (rung 2):** measured frame times over a sustained session on a real
device, not a benchmark loop.
**Note:** a fixed-timestep deterministic engine has a specific failure mode
here — it does not slow down gracefully, it accumulates. Worth measuring before
it is worth optimising.

### 9. Accessibility past contrast
**Cue:** *"What is unusable here for someone the APCA work did not cover?"*
**Evaluator (rung 1/2):** the palette already refuses to carry magnitude on hue
(≈8% of men). Extend to touch target sizing under system font scaling, motion
reduction for the 4D rotation, and screen-reader labelling of a board whose
state is currently visual only.
**Why it is Wave C:** it is real work with real value, and it is not what stops
you testing today.

### 10. The multiplayer sync claim, on a real network
**Cue:** *"`frame.ts` proves two peers agree; what proves they agree at the same
wall-clock moment, over a link that drops packets?"*
**Evaluator (rung 1):** fault injection — latency, reordering, a dropped peer —
against the existing `FrameChain`.
**Why last:** the byte-for-byte determinism underneath is done and proven. The
transport is not built, and building it before there is a playable single-player
surface would be inverting the dependency order.

## How to run any of these

```
Reference the current goal and EINCOL.md and follow the protocol exactly.
Cue for step 1: "<the cue from the item above>".
Use the highest evaluator rung available and report what it found that you did not.
Stop before implementing anything beyond the item's stated scope.
```

Two protocol notes that apply to every item here:

- **The negative control is not optional.** For each, ask what evidence would
  look identical if the feature were absent. Item 2 is the clearest case: a
  pixel-reading check that also passes on a blank frame has measured nothing.
- **Expect the first formulation to be wrong.** In the three runs so far, the
  instrument disagreed with the author every time — a phrase-grep that measured
  vocabulary, an oracle that missed a loaded die, three branches that had never
  executed. Budget for the correction rather than treating it as failure.

## Honest ordering caveat

Items 1–3 are sequenced by dependency and I am confident in that order. Items
4–7 are ranked by my judgement of risk to a submission, not by measurement —
they have not been through step 5, so treat the ranking as a proposal rather
than a finding. Item 6 in particular could turn out to be the most urgent thing
on the list if the copy reads worse than the mechanic is.
